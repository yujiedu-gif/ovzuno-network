This limitation matters when names and symbols appear in search results, token lists, wallet interfaces, or other materials. ## How to verify a WTK asset’s identity

Use a source-to-record check rather than relying on the ticker alone:

1. **Locate official project materials.** Look for a clear identification of the asset, its ticker, and the network on which it is issued or used. Check whether the project publishes a contract address or another distinguishing identifier. If the documentation is missing, unclear, or inconsistent, do not treat the identity as established.
2. **Confirm the network named by the project.** An identifier is meaningful only in the context of the relevant network. Do not assume that matching names on different networks indicate the same asset or record.
3. **Cross-check the published identifier against network records.** For a supported EVM chain, indexed explorer API resources can include balances, transactions, token transfers, contract source, and logs. The available endpoints, chains, fields, and access can change, so confirm that the service covers the network in question. ([source](<https://docs.etherscan.io/introduction>))
4. **Compare the exact identifier and network.** Check whether the network record corresponds to the identifier published in official project materials. A matching ticker or token name is not a substitute for this comparison.
5. **Record conflicts instead of resolving them by guesswork.** If project pages, listings, or network records show different networks or identifiers, the discrepancy remains material. Do not select one result merely because it is more visible or has a familiar name.

This workflow can help determine whether a project’s published identifier corresponds to a record on the stated network. It does not turn a ticker into a unique identifier, and the evidence available here does not supply WTK-specific project documentation or a network address to check. As a result, it cannot be used to reach a confirmed WTK identification.

Third-party listings may serve as starting points for locating possible project materials, but the evidence in this article does not establish that any listing is authoritative or conclusive. Treat a listing as a lead and look for an explicit project-to-identifier connection in official materials, then compare that identifier with records for the relevant network. If either part of that chain is unavailable, state what remains unverified.

When primary materials are available, distinguish what each source can show. Project documentation can state the project’s claimed network, identifier, and intended use. A network record can provide indexed information for an address or contract on the network it covers. Those are different kinds of evidence: a project statement describes what the project says, while a record supports a limited check of data associated with an identifier. Neither should be presented as proof of claims the source does not address.

For example, if documentation says an asset is intended for a particular use, report that as the project’s stated purpose. Do not silently turn that statement into a claim that the use is available, works as described, or has been independently verified. Likewise, seeing a contract or token record in an explorer does not, without further evidence, establish the project’s claims about its design or intended function.
