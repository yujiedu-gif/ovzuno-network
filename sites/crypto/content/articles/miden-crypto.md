## What should readers verify before relying on project claims?

Use the project’s current, attributable materials to check each claim in context. A practical review should establish:

- **Source and date:** Is the statement in official documentation or a technical specification, and when was it published or updated?
- **Version and status:** Does it describe a proposal, a test-stage feature, or a deployed capability? Which software or network version does it cover?
- **Technical detail:** Does the material explain the mechanism and its limits, or only state a goal? Can the claim be checked against a specification or other reproducible evidence?
- **Security and operations:** Are security, recovery, and operational claims supported by separate, current documentation? Do not treat a general project description as proof of an audit, recovery mechanism, or security outcome.
- **Independent assessment:** If a claim relies on independent testing, identify the test or assessment and what it actually covered. Do not infer independent verification from a project’s own description.

These checks help readers distinguish an architectural proposal from a working implementation without assuming either that a feature exists or that it does not. They also prevent a broad project description from being treated as evidence for a narrower claim about a particular version, network, security property, or operational condition.
