## What “AX crypto” can—and cannot—identify

“AX” and “AXS” are different text labels. Neither, by itself, establishes a unique asset, project, or blockchain. The evidence available for this article does not connect either label to a named project or confirm that they refer to the same thing. Treating them as interchangeable would therefore go beyond what can be verified.

A ticker-like label is a starting point for investigation, not proof of identity. A useful identification should connect the label to an official project name and, where applicable, to a particular network and token contract. Until those details agree, it is safer to describe the reference as unresolved than to infer a project from the abbreviation.

## Verify the project behind the AX or AXS label

Start with the source where you encountered the label. Record its exact spelling and any accompanying project name, network, or contract address. Then compare those details with the project’s own documentation and relevant technical records. The key question is whether the materials identify the same project and network, not whether a search result repeats the same letters.

For an onchain token, a contract address can help distinguish one token from another, but it should be checked against documentation that identifies the relevant network. Where an explorer is used, confirm that it is for the stated network and that the information shown corresponds to the address in question. ## Check whether staking or validators are actually documented

Once a project and network are identified, look for primary technical documentation that explicitly describes the network’s consensus and participant roles. A validator is a network role only where the project’s protocol documentation defines it. The presence of a token ticker or the word “crypto” does not prove that validators exist, that users can stake, or that a third party offers a staking service.

Keep protocol participation distinct from a service offered by a wallet, exchange, custodian, or staking provider. A project may describe validator participation without documenting user delegation; a service may describe a staking product without establishing that its terms are protocol rules. Verify each claim from the source responsible for it and state which layer the claim concerns.

## Read staking mechanics and risks from project evidence

If primary project evidence is found, check whether it actually specifies eligibility, delegation, reward calculation, lockups or withdrawal timing, and penalties. Do not assume these features are present or use rules from another network to fill a gap. Network rules and third-party product terms are separate evidence questions.

Also verify custody, recovery, fees, security claims, and service availability against the relevant protocol or provider documentation before describing them. For example, a documented validator commission on Solana applies to that network’s delegation model and is not evidence of a fee for an unrelated AX- or AXS-labeled project (`claim_solana_commission`). No reward rate, yield, lockup, unbonding rule, penalty, or service term for AX or AXS is established by the evidence available here.

A project’s documentation may change. When a specific mechanic is verified, identify the source and its applicable network or version, and avoid presenting a documented rate or outcome as guaranteed. If a detail is missing from the primary evidence, say that it is not established rather than borrowing a rule from a different protocol.
