## Why the name alone cannot identify a token

A name is a label, not enough evidence to establish which asset or project someone means. A search result, listing, or social profile using “Lucky Token” may point to material worth checking, but the name itself does not connect that material to a particular on-chain contract. Nor does it show that two assets with similar names are the same.

Metadata can add context, but it is not a substitute for identifying the asset. For example, an ERC-721 token may expose a URI that refers to metadata for a specific token ID. That reference does not by itself guarantee that the information or linked content will remain available, permanent, or accurate. [source](<https://eips.ethereum.org/EIPS/eip-721>) A name, image, or description shown by an interface should therefore be treated as a clue, not as proof of project identity.

The first useful question is not “What does Lucky Token do?” but “Which exact asset is this source describing?” If the source does not provide a network and a full contract address, you may not yet have enough information to answer that question. Avoid attributing a project’s claims to an asset based on a name match alone.

## What to verify for a lucky token crypto listing

Build a short evidence trail rather than relying on one page or one label:

1. **Capture the exact name and symbol.** Record the page or document where they appear. Note whether it identifies a network and gives a full contract address, rather than only a shortened address or ticker-like label.
2. **Confirm the network.** Check that the project materials and the independent record you consult identify the same blockchain. A match in name does not establish a match in network or contract.
3. **Compare the full contract address.** Use the complete address shown in project documentation and compare it with the address in the network-specific record. If the documentation gives no address, or if the addresses differ, the link between the name and the on-chain asset is not established by those materials.
4. **Check whether the sources point back to the same identifiers.** Project documentation should connect its description to the network and address. Independent records should be consistent with those identifiers. A discrepancy is a reason to report uncertainty, not to choose the version that appears more familiar.

A token’s chain and representation also matter when a provider describes which assets it supports. Supported assets can be specific to both a chain and a token representation; a shared symbol does not mean every version is interchangeable. [source](<https://developers.circle.com/circle-mint/supported-chains-and-currencies>) That claim concerns provider deposit support, not a general determination of identity, so use it only as a reminder to confirm the exact network and representation relevant to the record you are examining.

## How to assess project claims and token functions

Separate a project’s description from evidence about what a token or contract does. Documentation may state that a token has a function, but that statement should not automatically be presented as an independently verified fact. Record the claim, identify which source makes it, and look for evidence specific to the asset identified by its network and contract address.

For example, a project might describe a token as backed, redeemable, reward-bearing, or useful for access or governance. The name alone cannot verify any of those descriptions. If the evidence only supports the first, do not write the claim as though the latter has been established.
