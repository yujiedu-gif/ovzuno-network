Then compare those details with records for the named network. The point of this check is to see whether the identifier in the project material matches the identifier shown by the relevant network record—not merely whether a search result uses the same symbol.

Treat the network and identifier as a pair. A token name alone may not distinguish records on separate networks, and a network record that contains an identifier does not, on the evidence available here, establish that the record is an official QANX deployment. Attribution requires an explicit connection to an authoritative project source. If the project documentation lists several representations, check each one separately and record which specific network and identifier the claim concerns.

Use third-party listings and copied descriptions as discovery aids, not as final proof of identity. If a listing lacks a verifiable identifier, conflicts with the project’s own material, or does not specify the network, it leaves important questions unresolved. Note the gap and seek a current primary source rather than choosing whichever description appears most plausible.

For practical source handling, preserve the date and version of the documentation you consult, along with the network and identifier it names. Then state the result narrowly: what the source says, which record was checked, and what remains unconfirmed. No QANX-specific identifier or current network record is included in the permitted evidence for this article, so this process describes how to verify the details; it does not claim that verification has already occurred.

## What documentation can and cannot establish

Those records do not automatically establish broader claims. A stated use is not evidence of adoption, performance, security, or future availability. A deployment record is not, by itself, proof that the project’s claims about the asset are accurate. Do not treat a document about one version or network as universal without evidence that its scope extends further.
