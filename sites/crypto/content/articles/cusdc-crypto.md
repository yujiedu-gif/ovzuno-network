## Verify the token, network, and contract

Before using a cUSDC reference to make a payment decision, identify the particular deployment rather than matching only the displayed name. A useful verification sequence is:

1. **Find the project or issuer’s own documentation.** Confirm that it describes the exact token being discussed and explains its role. Do not assume a third-party label proves that the asset is official.
2. **Match the token identifier.** Compare the contract address, or the corresponding asset identifier used by that network, with the project’s documentation. A name or symbol alone is not a reliable substitute for that match.
3. **Confirm the blockchain network.** Ensure that the documentation and identifier refer to the same network as the wallet, recipient, or payment service. Support can depend on a specific chain and token representation; a service’s support for one version does not establish support for every asset with a similar symbol.
4. **Read the documentation’s description of the asset.** Determine whether it calls the token an issuer-created asset, a protocol-specific representation, or something else. If the source does not say, do not fill in the relationship by inference.

For Ethereum-compatible tokens, ERC-20 defines a common interface that includes balances, transfers, allowances, approvals, and related events. That interface can help describe how a token interacts with compatible software, but it does not establish the token’s issuer, backing, market value, compliance, or implementation safety. Nor does an ERC-20 interface alone prove that a token is cUSDC or related to USDC.
