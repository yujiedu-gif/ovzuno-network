## What “Sola crypto” can—and cannot—identify

A project, protocol, and token are different kinds of references. A project may describe a wider initiative; a protocol refers to rules or software; a token is an on-chain asset. One may be associated with another, but that relationship must be supported by evidence. A shared name, symbol, or logo does not establish that two references describe the same entity.

For a claimed token, a useful identification record includes the exact network and full contract address, alongside the name and symbol. Network context matters: a name or ticker alone does not identify a unique token record. Even an address should be checked against the claimed network and documentation; copying an address without establishing what it represents does not verify a project relationship.

## How to distinguish a token from a protocol or project

Read what the source describes, not just its heading or branding. Material describing software behavior or network rules may concern a protocol. Material describing an on-chain asset should identify the relevant token record. Organization or initiative materials may concern a broader project. These categories can be related, but the relationship needs explicit support; a token is not automatically the protocol or the project itself.

A token standard illustrates why category and identity should be kept separate. ERC-1155 allows one contract to manage multiple token types, including fungible, non-fungible, and semi-fungible configurations, with single and batch transfers. That describes a contract standard's capabilities; it does not identify a particular Sola reference or establish who issued it. ([source](<https://eips.ethereum.org/EIPS/eip-1155>))

Similarly, a technical record can support a claim about what a contract does without proving that the name attached to it is official. Look for a direct link between the project’s attributable materials and the exact network-and-address pair. If that link is absent, describe the record as a token record with an unverified relationship, not as a confirmed project token.

## Common name-matching mistakes

The first mistake is treating matching names, symbols, or logos as proof of connection. Such labels can serve as search clues, but they are not a substitute for a network and contract address supported by attributable evidence.

The second is treating a third-party listing or index entry as official confirmation. Listings and indexed data can help locate records, but their presence alone does not establish endorsement, project control, or current operation. Keep the source’s assertion separate from what the underlying record actually shows.

The third is assuming that searchable information is current or complete. An API documents particular endpoint families and supported chains, while a dataset schema describes records available through its own structure. Neither scope should be generalized into universal coverage. Check the relevant source’s current documentation and record when the identifiers were reviewed; if the source does not establish freshness, do not claim it does.

Finally, do not merge separate references because their branding looks alike. If network, address, or documentation differs, preserve that difference. A clear statement that the connection is unverified is more accurate than a definitive identification built from inconsistent clues.

## A practical checklist for evaluating a Sola reference

1. **Capture the reference.** Record the exact spelling and where it appeared. Note whether it claims to describe a project, protocol, token, or another thing.
2. **Record token identifiers, if applicable.** Write down the full network name and contract address. If either is missing, mark the token identification incomplete rather than guessing.
3. **Find attributable documentation.** Look for material that explicitly associates the claimed name with the same network and address, and describes whether the reference is a project, protocol, or token.
4. **Corroborate the on-chain record.** Compare the exact address on the stated network with independent records. Treat indexed information as corroboration of records, not as proof of official identity.
5. **Check agreement and scope.** Confirm that each source refers to the same network and address. Account for the source’s supported chains, endpoint coverage, and data structure; do not infer wider coverage than documented.
6. **Separate findings from open questions.** List what the evidence confirms, what conflicts, and what remains unknown. Do not resolve a mismatch by relying on a shared symbol, logo, or name.
