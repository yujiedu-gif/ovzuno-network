## How to verify a specific pool from primary sources

Begin with material controlled by the project or organization said to operate the pool. Look for an official document or announcement that uses the exact name and explains the relationship between the named organization and the pool. Check the source’s publication date and context: does it describe a current deployment, a proposal, a past service, or a third-party product? Those distinctions matter because a proposal or historical description does not confirm that a pool is currently deployed or operating.

If the source says the pool is on-chain, require the network and contract address. Compare those details with project-controlled documentation and a suitable block explorer. The network is part of the identification: an address presented without a matching network does not fully identify the deployment. Likewise, finding an address on a network does not, by itself, prove that it belongs to the claimed project or performs the advertised function. The project’s own documentation should connect the name, network, and address, and the on-chain record should be consistent with that information.

Treat search snippets, reposts, directories, and unofficial summaries as leads rather than confirmation. They may point toward a primary source, but they do not resolve identity or affiliation on their own. ## Which technical details matter once the pool is identified

Once a source has identified the entity, determine what the pool is intended to do. Its documentation should say what assets or other items are involved, which network it uses if applicable, and what participation means. In particular, check whether the arrangement involves depositing assets, swapping through a liquidity pool, staking, or some other mechanism. These are not interchangeable labels, and the generic word “pool” does not reveal which process applies.

If the identified system is a liquidity pool, inspect its own documentation for the assets held and the rules governing swaps or allocation. Do not borrow a familiar protocol’s description as a substitute. Uniswap v2 is one constant-product example, but other automated market makers can use different curves, assets, fees, and accounting. The exact mechanism must be supported by documentation for the pool or protocol being examined. The permitted evidence does not show that an “SBI crypto pool” uses any particular curve, asset pair, or accounting method.

Also identify any documented administrative controls. The relevant materials should clarify who, if anyone, can change parameters, pause activity, or upgrade the contracts, and what limits apply. This is a request for verifiable project-specific information, not a claim that any particular pool has those controls. Distinguish what documentation says the design permits from evidence about how the system is actually operating. The existence of a published description does not fill in missing details about a specific deployment.

A useful verification record keeps these details separate: the exact project or service name; the source and date that identify it; the stated function and assets; and, for an on-chain pool, the network, contract address, and documentation describing its mechanics and controls. If any item is absent or inconsistent, record that gap rather than assuming another pool’s design applies.
