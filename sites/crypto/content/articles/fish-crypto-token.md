## Why “FISH” alone may not identify a token

A short name, ticker, or symbol is a label, not a complete asset identity. It can help locate information, but a matching label in two places does not prove that those sources mean the same token. A sound identification needs context: which project is being discussed, which network is involved, and what identifier the project associates with the token.

Technical standards do not solve the identity question by themselves. For example, ERC-20 defines a common fungible-token interface, including functions and events for supply, balances, transfers, allowances, and approvals. But that interface does not identify the project or determine issuance policy, backing, market value, compliance, or whether an implementation is safe. [source](<https://eips.ethereum.org/EIPS/eip-20>)

That distinction matters when a reference comes from a search result, social post, exchange listing, or community discussion. Those sources may use a short label without supplying enough information to distinguish one asset from another. A name or symbol should therefore be treated as a clue to investigate, not as proof of identity or a basis for assigning functions or rights.

## How to identify a fish crypto token reference

Start with the original source of the reference. Find the project’s stated full name and the network on which it says the token exists. Then look for a contract address or another authoritative identifier tied to that network. If the source does not provide those details, the reference remains unresolved; filling in missing information from a similarly named listing would not establish which asset the source intended.

Next, compare the identifier with the project’s own documentation. The documentation should connect the token name, network, and address or other identifier. Then check the relevant network’s public records for that same identifier. The project documentation and network record answer different questions: one shows what the project says the token is, while the other can help confirm that the cited identifier corresponds to a record on the stated network. Neither a matching ticker nor a third-party listing alone completes that comparison.

For an Ethereum ERC-20 reference, use the contract address together with the network rather than relying on the token symbol alone. A contract address is meaningful in its network context; a source that omits the network leaves an important part of the identification incomplete. If two references use the same name but provide different addresses or networks, do not combine them into a single entry without evidence that connects them.

Also distinguish a project’s token from a representation that may exist on another chain. Supported tokens and deposit destinations can be chain- and representation-specific; a provider’s support for one version does not establish support for every token with the same symbol or for bridged variants. [source](<https://developers.circle.com/circle-mint/supported-chains-and-currencies>) This is a reason to check the exact network and representation cited, not a claim about any particular provider or FISH token.

A practical record of the check can be brief: write down the project name as given, the claimed network, the exact address or identifier, and the project documentation page that links them. If one source gives a different address, a different network, or no identifier at all, mark that discrepancy as unresolved. Do not resolve it by choosing whichever result appears most familiar.

## What the project says the token does

After identifying the asset, separate the project’s description of intended function from facts independently supported by the network record. Use clear attribution, such as “the project describes the token as serving this purpose.” That wording reports a claim without treating it as proof that the claimed function operates as described.

Read the documentation for an explanation of the claimed role and any systems it depends on. If the project uses terms such as “utility” or “governance,” look for the specific actions or mechanisms described rather than treating the label as a complete explanation. The phrase “utility token,” for example, denotes an intended project- or protocol-related function, not a universal technical token standard.  This general terminology does not establish that a particular FISH token performs a stated function.

Do not infer ownership rights, backing, redemption, or enforceable claims from a name, symbol, or interface standard. The ERC-20 interface describes how compatible applications can interact with certain token functions; it does not establish what a token represents or what a holder is entitled to receive. [source](<https://eips.ethereum.org/EIPS/eip-20>) Those questions require evidence specific to the project and its arrangements, and the information available here does not provide that evidence for a FISH asset.

Metadata should also be read within its limits. An ERC-721 token can expose a URI that refers to metadata for a token ID, but the standard does not guarantee the availability, permanence, accuracy, or licensing of the referenced content. [source](<https://eips.ethereum.org/EIPS/eip-721>) A displayed name, image, or description may help explain what an application presents, but it does not independently verify broader project statements.

## Assessing claims and limitations

Keep the evidence in separate categories. A network-specific identifier helps distinguish the asset being discussed. Project documentation supports an attributed account of what the project says the token is meant to do. Claims about legal status, rights, backing, performance, or operational protections require separate evidence appropriate to those subjects.

For example, a third-party tokenized-security model may involve a custodial entitlement or synthetic instrument rather than direct ownership of the referenced security, with rights depending on the structure and governing documents. [source](<https://www.sec.gov/newsroom/speeches-statements/corp-fin-statement-tokenized-securities-012826-statement-tokenized-securities>) This illustrates why a token record alone cannot settle what a holder’s rights are. It does not imply that a FISH token is a security or uses that model.
