## Verify XIN crypto against primary project and network records

Start with documentation published by the project and the relevant network. Look for a direct, consistent connection among the project name, the exact asset name or ticker, and the network where the asset exists. If the records do not make that connection, keep the identification unresolved rather than selecting a similarly named asset.

Next, look for the network’s authoritative identifier for the asset. For a token, that may be a contract address on the named chain; a native asset would need to be identified by the network’s own records. Compare any identifier in project materials with the corresponding network documentation or record. A third-party listing may help locate possible records, but it does not replace confirmation from the project and network themselves.

If the project describes assets on more than one chain, do not assume that records on separate chains are interchangeable. Cross-chain transfers coordinate value between otherwise isolated blockchain environments; the destination-side record changes only after bridge-side logic accepts the relevant message or transfer condition. Security therefore depends materially on how the source-chain event is verified, and descriptions such as “trusted” or “trustless” do not remove contract, governance, chain, or operational risk. These general bridge considerations do not establish that any XIN asset is bridged or available on multiple networks. ([source](<https://ethereum.org/developers/docs/bridges>))

A practical evidence note can record the exact name, network, identifier, source, and the date you checked the record. If a project or network page is unavailable, contradictory, or does not state an identifier, document that gap. Do not fill it using a ticker search result or a supposed resemblance to “cryptoxin.”

## Check whether the documented system actually uses staking and validators

Once an asset and network are positively identified, look for protocol documentation that explicitly connects them to staking and validators. The documentation should describe the validator role and how participation is assigned or authorized. A general page about staking, or a service that advertises a staking product, does not on its own establish that the identified network uses that protocol mechanism.

Keep protocol mechanics distinct from intermediary services. For example, Solana documentation describes a specific native delegation model in which a delegator can assign stake to a validator, increasing that validator’s consensus weight while the delegator retains token control under the stake-account model. This is an example for Solana only; it does not establish how XIN works or whether XIN is connected to Solana. ([source](<https://solana.com/docs/references/staking>))

If the XIN project’s primary documentation does not identify validator duties, participation rules, and the relationship between the asset and the protocol, describe the staking-validator connection as unverified. Avoid importing mechanics from another network merely because the term “staking” appears in a listing or promotional description.
