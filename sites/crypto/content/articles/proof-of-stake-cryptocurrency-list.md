A proof-of-stake cryptocurrency list should identify networks whose consensus design uses stake, name each network’s native asset separately, and qualify any hybrid or protocol-specific distinction. The evidence available for this article confirms Ethereum as a proof-of-stake network and identifies Decred as a hybrid network combining proof of work and proof of stake; it does not support a broad, current catalog of additional networks. Treat the entries below as evidence-bounded examples, not a complete market list or an assessment of staking products.

## How this proof of stake cryptocurrency list is defined

An entry belongs on this list only when the evidence identifies the network’s consensus design as using proof of stake. That criterion concerns how the network participates in consensus; it does not mean that every holder can validate, delegate, or stake through a particular application or provider.

The network and its native asset are separate labels. A consensus mechanism describes a network protocol, while the asset used in that protocol is a token or cryptocurrency. A third-party service offering staking does not, by itself, establish that the underlying network uses proof-of-stake consensus.

The available evidence supports Ethereum’s proof-of-stake classification and describes Decred’s hybrid design. It does not establish a verification date for a current, comprehensive list, so this reference should not be read as exhaustive or as a live status check. Verify any classification against current primary network documentation before relying on it.

## How to verify a network’s consensus design

Start with the network’s current protocol specification or official technical documentation. Look for an explicit description of the consensus mechanism and the roles that validators or other participants perform. If the documentation describes a hybrid mechanism, preserve that qualification rather than reducing it to a simple yes-or-no label.

Then check what the described mechanism applies to. A protocol’s consensus process is different from a wallet, exchange, pooled product, or liquid-staking arrangement offered around the network. The presence of a service that accepts deposits or distributes staking-related receipts does not independently prove how the base network reaches consensus.

Finally, record the source and the date checked. Protocol descriptions can become stale when network rules change. For Ethereum, the documented proof-of-stake model includes attestations, fork choice, and checkpoint finality; those features should be attributed to Ethereum rather than assumed to apply to every proof-of-stake network. For a hybrid network such as Decred, verify which responsibilities are assigned to each component.

## What this list does not tell you about staking

A consensus classification does not show that a particular person can participate directly, or that a particular wallet, exchange, or provider supports participation. It also does not establish a service’s custody arrangement, fees, rewards, lockup terms, or recovery process. Those are separate, provider- and product-specific questions that require current evidence.

Ethereum’s protocol incentives illustrate why consensus evidence should not be mistaken for a return promise: its validator incentives include rewards for correct participation, missed rewards or penalties for inactivity, and slashing for specified conflicting messages. This describes protocol-level incentives, not an expected return or a recommendation to participate. It does not establish the terms of third-party services.

The list is not a yield comparison, security ranking, or investment assessment. A proof-of-stake label alone does not establish that a network, asset, validator, or service is safe or suitable for a reader. No asset is ranked here.

## Limits, changes, and jurisdiction-specific considerations

Network upgrades and governance decisions can change consensus rules or participant roles. A classification should therefore be treated as time-sensitive: check the current protocol documentation and note when it was reviewed. Where evidence does not confirm the active design, mark the status as unverified rather than filling the gap with assumptions.

Practical staking availability, fees, and terms may depend on a particular provider and jurisdiction. The evidence here does not establish legal or tax treatment, nor does it support claims about service availability, fees, yields, or compliance. Those points require separate, current, jurisdiction-specific or provider-specific evidence and should not be generalized from the network’s consensus mechanism.

Use this list to orient a technical check, not to decide whether to hold or stake an asset. Confirm the network, native asset, consensus classification, any hybrid qualification, and the date of the source before treating an entry as current.
