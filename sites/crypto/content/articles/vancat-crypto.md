## How to verify a Vancat project identity

Begin with materials attributable to the project itself. Look for documentation that names the project and gives consistent identifiers, such as a blockchain network and a contract address, if applicable. A project’s own statement is useful evidence of what it claims, but it should not be confused with independent confirmation. If the details are missing, ambiguous, or inconsistent, record the gap rather than guessing.

Next, compare any stated address and network with relevant blockchain records. Those records can corroborate technical facts about an address and activity recorded on a network. They do not, by themselves, prove that the address belongs to the project named in a website, social post, or third-party listing. To make that connection, attributable project materials must identify the same address and network.

Keep the network attached to every address reference. A project name, ticker, and contract address are different kinds of identifiers; do not treat them as interchangeable until reliable materials link them. If two sources list different addresses or networks, preserve the conflict and seek clarification rather than selecting the most repeated version.

A concise verification record can note the exact name used by each source, its publication or update date when available, the claimed network and address, and the technical record used for comparison. Distinguish source assertions from corroborated details. Mark absent information as unknown. This simple separation makes it easier to see whether sources actually refer to the same project.

## What evidence can establish its stated function

Project documentation can establish what a project says it is intended to do. That is evidence of a stated purpose, not automatic proof that the system performs as described. Code or technical records can support narrower claims about behavior, but only when the material demonstrates that specific behavior and is reliably connected to the project being discussed.

For example, Filecoin’s Proof-of-Spacetime is designed to let a storage provider prove to the network that it continues to store a unique copy of committed data. That is a description of one protocol-specific mechanism. It does not show that a project using storage-related language employs that mechanism, and it provides no evidence about Vancat.

Separate the claims you are evaluating. A project page might describe an intended function, while a blockchain record might show activity at an address. Neither fact alone necessarily connects the project’s stated purpose to the recorded activity. That link requires consistent, attributable evidence tying the named project to the relevant address and technical components.

Do not infer utility, adoption, security, or value from a name, ticker, promotional description, or the existence of an address. These are distinct claims that require evidence suited to each one. If documentation states an intention but available technical evidence does not demonstrate the corresponding behavior, describe the intention as a project statement and leave performance unverified.

## A concise checklist before relying on claims

- Confirm the exact project identity; do not rely on a name or ticker alone.
- Find attributable project materials that identify the network and, if applicable, a contract address.
- Compare the stated identifiers with relevant technical records, while distinguishing what those records show from who claims the address.
- Match each function claim to documentation or technical evidence that supports that particular statement.
- Keep source attribution, dates, conflicts, and unresolved questions visible.
- Treat availability, fees, yields, security, recovery, and compliance as unknown unless current, project-specific evidence supports them.
